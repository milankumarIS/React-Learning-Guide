01

What is a side effect?

useEffect & Side Effects

What is it?

Work that interacts with something outside React rendering, such as subscriptions, timers, browser APIs, connections or network synchronization.

🧠 Layman example

Like writing a shopping list versus actually calling the delivery company. The list describes; the call changes something outside it.

When / why would you use it?

Use effects for synchronization with external systems, not merely because code needs to run after rendering.

Practical example

useEffect(() => { const connection = connect(); return () => connection.disconnect(); }, []);

02

Effect lifecycle

useEffect & Side Effects

What is it?

An effect has setup, may rerun when dependencies change, and may clean up before the next relevant setup or when the component is removed.

🧠 Layman example

Like renting a meeting room: set it up, use it, then clean it before another booking or when the booking ends.

When / why would you use it?

Use lifecycle thinking whenever an effect creates a resource that must later be updated or released.

Practical example

useEffect(() => { const c = connect(roomId); return () => c.disconnect(); }, [roomId]);

How to approach / expected direction

Think about synchronization with the new dependency value.

2. What should you ask whenever an effect creates a resource?
How to approach / expected direction

Look for setup/cleanup symmetry: subscriptions unsubscribe, timers clear, connections disconnect.

Dependency array

useEffect & Side Effects

What is it?

The dependency array tells React which reactive values an effect depends on and when synchronization may need to rerun.

🧠 Layman example

A delivery instruction can say: recalculate whenever the address or package changes. Those are dependencies.

When / why would you use it?

Use dependencies to describe values read by the effect that can affect the synchronization.

Practical example

useEffect & Side Effects

useEffect & Side Effects

08

Fetching API data

useEffect & Side Effects

What is it?

Effects can handle basic client-side fetching when fetching is part of synchronization, although larger applications may use dedicated data-fetching solutions.

🧠 Layman example

A component needs to keep its displayed customer data synchronized with the selected customer ID.

When / why would you use it?

Use for simple cases; later sections of the guide cover dedicated data-fetching and cache tools.

Practical example

useEffect(() => {
  let ignore = false;
  async function load() {
    const r = await fetch(`/api/users/${userId}`);
    const data = await r.json();
    if (!ignore) setUser(data);
  }
  load();
  return () => { ignore = true; };
}, [userId]);

1. Why can an older request need protection from updating state after a newer request starts?
How to approach / expected direction

Think about out-of-order asynchronous responses.

2. What loading, error, empty and success states should a real UI consider?
How to approach / expected direction

Go beyond fetch-and-setState; consider all user-visible request states.

Avoiding unnecessary effects

useEffect & Side Effects

What is it?

Not every calculation or action belongs in an effect. Derived values can be calculated during render and user-triggered actions usually belong in event handlers.

🧠 Layman example

You do not call an outside worker just to add two numbers; but you might need synchronization to an external payment system.

When / why would you use it?

Use effects for synchronization, not as a general 'run this later' mechanism.

Practical example

const fullName = `${firstName} ${lastName}`;

function handleSubmit() {
  saveOrder(order);
}

Intern questions

1. Why might setFullName(firstName + lastName) inside an effect be unnecessary?
How to approach / expected direction

Look for derived data versus synchronization.

2. Why is saving after a submit usually better in the submit handler?
How to approach / expected direction

The submit event directly causes the action; an effect watching state can couple it to unrelated renders or changes.

useEffect & Side Effects

What is it?

Effects synchronize with external systems; event handlers respond directly to a user interaction.

🧠 Layman example

A button click is like a customer pressing a service bell—the action happens because the bell was pressed.

When / why would you use it?

Use handlers for clicks, submits and user actions; effects for reactive synchronization.

Practical example

  event.preventDefault();

Race conditions

useEffect & Side Effects

What is it?

A race condition can occur when overlapping async operations finish out of order and an older result overwrites newer state.

🧠 Layman example

You order two taxis; the first request arrives last. Taking whichever arrives last may send you the wrong way.

When / why would you use it?

Use cancellation or ignore-obsolete-result strategies when only the latest request should update the UI.

Practical example

useEffect(() => {
  let ignore = false;
  fetch(`/api/search?q=${query}`)
    .then(r => r.json())
    .then(data => { if (!ignore) setResults(data); });
  return () => { ignore = true; };
}, [query]);

Intern questions

1. How can query A finishing after query B produce the wrong UI?
How to approach / expected direction

Explain out-of-order completion.

2. What should determine whether an async result is still allowed to update state?
How to approach / expected direction

The result should still correspond to the current relevant request/input.

AbortController

useEffect & Side Effects

What is it?

AbortController can signal cancellation to fetch, allowing obsolete network work to be cancelled rather than merely ignored.

🧠 Layman example

If you order the wrong item and immediately cancel it, cancellation is different from waiting for delivery and throwing it away.

When / why would you use it?

Use when cancelling obsolete fetch requests is appropriate.

Practical example

useEffect(() => {
  const controller = new AbortController();
  fetch(`/api/search?q=${query}`, { signal: controller.signal });
  return () => controller.abort();
}, [query]);

Intern questions

1. How is aborting a request different from merely ignoring its result?
How to approach / expected direction

Distinguish cancelling underlying work from preventing its result from being applied.

2. Why does the controller belong in the cleanup of the effect that created it?
How to approach / expected direction

Cleanup marks that request as no longer relevant to the current synchronization.
